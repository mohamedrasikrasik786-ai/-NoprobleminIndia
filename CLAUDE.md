# No Problem in India — critical document-structure fix (read this first)

`landing-page.html` had **no `<!DOCTYPE html>`, `<html>`, `<head>`, or `<body>` tags at all** — it started directly with a bare `<title>` — until this was fixed. Browsers silently auto-correct that into an implied structure, which is exactly why it went unnoticed for the entire hero/community/footer redesign: desktop rendering looked completely normal. But it also meant there was **no `<meta name="viewport" content="width=device-width, initial-scale=1">` tag**, and that one omission broke mobile everywhere it actually mattered: on a real phone, with no viewport tag, the browser defaults to a ~980px virtual viewport and shrinks the whole desktop layout to fit the physical screen — the `max-width:899px` mobile media queries never fire at all, no matter how correct the mobile CSS is. The client's real-phone screenshot showed exactly this (tiny desktop layout, not the mobile design).

**This also retroactively explains the "ghost 980px width" bug documented multiple times earlier in this file** — `resize_window` to widths below ~750px in the testing tool was reporting `window.innerWidth: 980` and computing desktop styles, which was worked around by testing mobile CSS at 800px instead. That was never a testing-tool quirk. It was Chromium reproducing this exact real bug (defaulting to the 980px layout viewport) at narrow explicit sizes, while wider requested sizes happened to sit above whatever internal heuristic threshold suppresses that default. The workaround (test at 800px, trust the mechanism generalizes down to real phone widths) happened to be sound engineering, but the root cause was always fixable and should have been checked first, before it was checked last.

Fixed by wrapping the existing content in a proper `<!DOCTYPE html><html lang="en"><head>...<meta charset="UTF-8"><meta name="viewport" content="width=device-width, initial-scale=1">...</head><body>...</body></html>` — `<head>` closes right before the first visible markup (the `<style>` block ends there), `<body>` wraps everything from the hero's checkbox-hack input through the closing `</script>`. Verified after the fix: a real `390px` `resize_window` call now correctly reports `window.innerWidth: 390` (not 980) and every mobile breakpoint fires as designed. **If mobile styles ever appear to stop working sitewide again (not just one section), check for this tag before anything else** — it's a single point of failure for the entire responsive system.

## Usage rules

- **CTA buttons** (primary action, e.g. "Start Here", "Shop on WhatsApp"): `--color-primary` background, white text, `--color-primary-hover` on hover.
- **Secondary buttons/links**: `--color-accent` background or outline (`.btn-ghost`).
- **Section backgrounds**: alternate `--color-bg-base` and `--color-bg-alt` between sections instead of all one color. The header, the Farm & Products section, and the final CTA section are deliberate exceptions — they use `--color-dark` as a bold, dark-green brand bookend.
- **Headings**: `--color-dark` or `--color-text-primary`, never pure black.
- **Body text**: `--color-text-body`.
- **Small accents** (icons, dividers, footer labels): `--color-brown`, used sparingly, never as a dominant color, and only on light backgrounds (it has poor contrast on `--color-dark`).

## Site-wide horizontal gutter

The page's left/right margin is a single `--gutter` custom property (defined in `:root`, alongside the color tokens): **64px desktop, 40px tablet (≤1024px), 16px mobile (≤640px)**. `.wrap` (the shared max-width:1180px container used by nearly every section) reads `padding-inline:var(--gutter)`, and `.hero-v2-header` (the only full-bleed element with its own horizontal padding, since it isn't wrapped in `.wrap`) reads `padding:20px var(--gutter)` (`16px var(--gutter)` on its own <900px mobile override). Component-level paddings (card padding, drawer padding, badge padding, etc.) are unrelated to this and were left alone — only the outer page gutter follows `--gutter`. If a new full-bleed element ever needs the page gutter, reference `var(--gutter)` rather than hardcoding a pixel value.

## Deploying (current, actual process)

The MCP-based Vercel tools cannot handle a 4+MB file (payload size limits on `create_deployment`/`upload_file`, and the `Read` tool itself can't load a file with multi-MB single lines). The working method is the local Vercel CLI, run from a clean scratch folder (never deploy this project's own working directory directly — it has unrelated stray files like an old `index.html`/`styles.css`/`image 19.png` that don't belong on the live site):

```bash
rm -rf /tmp/npii-deploy && mkdir -p /tmp/npii-deploy
cp "landing-page.html" /tmp/npii-deploy/index.html
cd /tmp/npii-deploy
npx vercel link --yes --project no-problem-in-india   # first time / new machine only
npx vercel --prod --yes
```

- The local file **must** be named `index.html` and sit directly at the deploy folder's root, **not** inside a `src/` subfolder — the linked Vercel project's own `rootDirectory` setting remaps it to `src/index.html` server-side automatically. Deploying with `src/index.html` locally produces a broken double-nested `src/src/index.html` and a 404 (this was hit once, see the error log elsewhere in this file for the full story).
- Live URL: `https://no-problem-in-india.vercel.app`. Requires being logged in (`npx vercel whoami`) — the client (Rasik) has logged in from this machine before; if a fresh machine shows no login, that's a step to run in an interactive terminal, not something an AI agent can do (Vercel API tokens for CLI login require a human to complete an OAuth flow / paste a token).
- **Never deploy without the user explicitly saying "deploy"** — this is a standing rule, not a one-time preference. Every other change (local file edits, Claude Artifact publishes) happens freely; only pushing to the live Vercel site needs that explicit go-ahead each time.
- **Never redeploy to Vercel automatically after an edit.** Only push a new deployment when the user explicitly says "deploy". Local/Artifact updates are fine on every change; the live site is not.

## Hero section (Figma redesign)

The hero (`.hero-v2` + `.hero-v2-header`) was rebuilt from two Figma frames (node-id `1051-71` desktop, `1053-849` mobile) and is a deliberate departure from the rest of the page's design system:

- **Font**: the headline uses `'Plus Jakarta Sans'` (800 weight), not Fraunces — Figma specified `Cal Sans`, which isn't on Google Fonts, so Plus Jakarta Sans is the closest available substitute. This is scoped to the hero headline only; the rest of the site still uses Fraunces for headings.
- **Yellow accent** (`--color-yellow: #F6CE40`): used only for the hero's own "Book a Farm Visit" button and the couple-photo's blob-mask background. Every other CTA on the page stays green (`--color-primary`) — this was a deliberate Figma-specified exception, not a mistake.
- **Blob mask**: the oval cutout around the couple photo (`.hero-v2-blob`) is the exact vector path exported from Figma (a circle-minus-ellipse boolean op), not a hand-drawn approximation. Reuse the same path at different sizes for other breakpoints rather than redrawing it.
- **Header behavior**: `.hero-v2-header` is `position:fixed`, transparent by default (sitting on top of the hero images/yellow block). JS (`syncHeroHeader` in the bottom `<script>`) adds a `.scrolled` class once you scroll past the hero. Per Figma node `1053-144` (the scrolled-state design), `.scrolled` switches the bar to a solid **`--color-bg-base` (white/cream)** background, not dark green — brand text stays `--color-dark` in both states, and the logo icon grows from 34px to 44px with a smooth transition. - **Navigation — two different treatments by width**:
  - **>=1340px** ("real" desktop): no hamburger at all, ever. Instead, `.hero-v2-navlinks` (inline text links, matching Figma node `1053-144` exactly: black `Work Sans` text, green pill CTA) sits hidden (`opacity:0`, translated up) inside the transparent hero-top header and smoothly fades/slides in only once `.scrolled` is active — this is the "nav bar comes in with smooth animation on scroll" behavior. Figma's hero-top mock (`1051-71`) never shows these links, only the scrolled mock does, so gating them behind `.scrolled` is exactly what both frames specify together.

This threshold is **not** the same as the hero's 900px image breakpoint. This HTML restructure was done with a small Node script (`fs.readFileSync`/`indexOf`/`writeFileSync` on exact short anchor strings) rather than the `Edit` tool, because each `.gallery-item`/`.testimonial-card` still sits on a single line containing a full base64-embedded photo — those lines are large enough that even a 1-3 line `Read` of that region exceeds the tool's token ceiling, so the surrounding HTML can't be quoted as `old_string` context the normal way. If this section's HTML needs surgical editing again and a `Read`/`Edit` call errors with "exceeds maximum allowed tokens," don't fight it — write a short throwaway Node script to scratchpad that does exact-string `indexOf`+slice replacement (throwing if the anchor isn't found or isn't unique) instead.
- Because the grids are now full-bleed, they need their own desktop centering (previously provided free by being inside `.wrap`): both got `max-width:1180px; margin-inline:auto; padding-inline:var(--gutter);` added directly to their base (non-mobile) rule. Verified this reproduces `.wrap`'s exact left edge at desktop widths (both grids' `getBoundingClientRect().left` matches `.wrap`'s own, at `1440px` wide).
- Mobile (`≤760px`) now uses **the exact same padding formula as `.journal-carousel`**, copied verbatim rather than reinvented: `padding-left:max(24px, calc((100% - 1180px)/2 + 24px)); scroll-padding-left:max(24px, calc((100% - 1180px)/2 + 24px));`, with `max-width:none; margin-inline:0; padding-inline:0;` to cancel the desktop centering rule above. This is a deliberately **hardcoded `24px`, not `var(--gutter)`** (mobile gutter is `16px`) — matching Journal's literal value was the point, so all three carousels (Journal, Testimonial, Gallery) align to the exact same left inset and bleed the same way off the right edge, rather than each computing a slightly different edge position from the gutter token. `.gallery-item`/`.testimonial-card` mobile width is `78vw; max-width:340px` (Journal's own `.j-card` numbers) — was `72vw`/`82vw` with a mixed 320/340 max-width in the earlier, since-replaced version. `gap` is `20px` (was `14px`/`16px`), `padding-block` is `6px 12px` (was `6px 4px`) — again Journal's own values.
- No prev/next arrow buttons were added to either carousel (Journal has `.car-btn` prev/next; Testimonial/Gallery are swipe/scroll-snap only) — the ask was to match the padding/margin/scroll mechanics, not to add navigation UI, and adding buttons to two of three carousels but not all three would be its own inconsistency.

## Mobile footer had a real ~33px black gap below the card — `min-height:100%` doesn't resolve the way it looks like it should

Client reported a black empty strip below `.footer-card` on mobile, plus asked why the "Rooted in red earth" heading looked cut off. The heading being covered is **expected** — it's just the fixed-position header floating on top of scrolling content, not a bug. The empty strip was a real bug, though, and a subtle one:

- `.footer-new{min-height:100%;}` (inside the `≤899px` query) was meant to make the footer's flex column fill the SAME height as its parent `footer{min-height:100vh; min-height:100dvh;}`, so `justify-content:flex-end` could pin `.footer-card` flush to the true bottom of the screen. **It doesn't work**: percentage heights only resolve against a parent with an explicitly *specified* height — a parent whose height is `auto` but happens to be constrained by `min-height` does **not** count, per spec. So `.footer-new`'s `min-height:100%` computed to `auto`, meaning `.footer-new`'s actual height was just its own content's height (heading + card), which came in about 33px shorter than the full `100dvh` `footer` box. `justify-content:flex-end` then had nothing to push against, and that 33px showed as bare black background (`.community-footer-bg-wrap{background:#000}`) below the card.
- **Verified via `getBoundingClientRect()` comparison** (`footer-new`'s bottom vs. `footer`'s own bottom edge, not visually — screenshots at this scroll depth are unreliable, see the community/footer section's existing screenshot-tool note above) that the two didn't match before the fix and match exactly after it.
- **Fix**: give `.footer-new` its own `min-height:100vh; min-height:100dvh;` directly instead of `min-height:100%` — skip the percentage-of-parent indirection entirely, since nothing actually required routing through `footer`'s box. If this footer-height mechanism needs touching again, don't reintroduce a bare `min-height:100%` on a flex child whose parent's height itself comes from `min-height` rather than an explicit `height` — it silently no-ops.
- This bug likely predates this session's edits and was probably always losing a similar amount of space; it likely became visible/noticeable only now because of small height changes elsewhere in this pass (strip padding, gallery button, corner-radius additions) shifting exactly how much slack was left. It was not caused by, and has nothing to do with, hero image sizing.

## Mobile "Rooted in red earth" parallax felt broken — it wasn't the JS, it was a ~230px dead-black gap before it

Client reported the mobile scroll-parallax on `.footer-rooted`/`.footer-card` "wasn't working" and that the long community→footer scroll felt pointless. **The parallax JS was never actually broken** — confirmed live via `getComputedStyle(el).transform` at different scroll positions (e.g. `matrix(1,0,0,1,0,17.9)` vs `matrix(1,0,0,1,0,-24.6)`), so `updateFooterParallax` was firing and updating correctly the whole time.

**The real problem**: on tall modern phones (812–932px viewport height), `.final`'s mobile `min-height:100vh` forced the section to be much taller than `.final-photo` actually renders. The photo is sized by width (`width:100%; height:auto`), so its rendered height is fixed by its own aspect ratio (`2305/1440 ≈ 1.6`, i.e. `~160vw`) — completely independent of viewport height. On an ~812px-tall viewport at 375px wide, the photo renders ~600px tall inside an 812px-tall forced box, leaving **~210px of flat solid black** before `.final` even ends, and then more black before the footer's "Rooted in red earth" heading appears. Moving text over a flat, textureless black background produces **zero visible depth cue** — there's nothing for the eye to compare the motion against — which is exactly why the animation read as "not working" even though it was technically running. This also directly explains the "long scroll feels unpurposeful" complaint: that ~200px+ stretch had no visual content in it at all on tall devices.
- **Root cause, more precisely**: this mobile bleed effect was tuned against the client's own reference numbers (photo ≈608px + ≈72px bleed ≈ 680px total, see the Community & Footer section notes above) — a reference height *shorter* than most current phones (812–932px). The design was only ever screenshot-verified at an 800px-**wide** viewport standing in for mobile (a documented limitation, see "Testing caveat" above), never at a true narrow width with a *tall* real-device height, so this mismatch was never actually caught before.
- **Fix**: `.final`'s mobile `min-height` changed from a flat `min-height:100vh; min-height:100dvh;` to `min-height:min(100vh,165vw); min-height:min(100dvh,165vw);` — `165vw` is just above the photo's natural `~160vw` rendered height (small buffer for the fade to read as intentional, not abrupt). `min()` means: on short/wide viewports `100vh` still wins (unchanged behavior, no regression there); on tall/narrow viewports (the actual problem case) `165vw` wins instead, so `.final`'s box shrinks to hug the photo almost exactly, cutting the dead space to a genuinely small handful of pixels (verified: photo-bottom-to-heading-top gap went from ~236px down to ~5px on a real 375×812 test). CTA content (`.final .wrap`, ~375px tall including padding) comfortably fits inside the shrunk box with room to spare, so nothing overflows or clips — `min-height` only ever raises a floor, never caps content, so this change carries no clipping risk even if that math is ever slightly off for some future content change.
- **Also amplified the parallax itself** while fixing this, since the effect should be more clearly *felt* now that there's real photo texture for it to move against: mobile's shared-offset factor went `0.06 → 0.14` and its clamp went `±15% → ±28%` of the heading's own height. This is safe to push further than the old conservative tuning suggests — the "zero natural gap causes overlap" risk documented earlier only applies to *independent* per-element rates drifting apart; the shared single-offset approach moves both elements by the *identical* amount always, so there is no relative motion between them and therefore no overlap risk at any magnitude. Don't reintroduce independent per-element factors on mobile without re-solving that original overlap problem first.
- **Do not touch the footer's own `min-height:100vh`/`100dvh`** while working in this area — that one is intentional and load-bearing for a different reason (giving `justify-content:flex-end` enough slack to visibly pin the heading+card to the true bottom of the screen, and giving the parallax room to play out across the scroll). Only `.final`'s min-height was wrong; the footer's was correct all along.
